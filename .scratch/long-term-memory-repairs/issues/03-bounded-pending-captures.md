# 03: 记忆接收积压纳入容量预算并向入口背压

**What to build:** 记忆存储容量不足或不能提交时，待接收经历也保持有界；前台明确区分已经接收与暂未接收的材料，空间释放后可以恢复补送，不把无限增长转移到业务数据库。

**Blocked by:** None (can start immediately).

**Status:** ready-for-agent
**Labels:** ready-for-agent
**Priority:** P1
**Spec:** [长期记忆规格](https://github.com/NoClickView/dsh-superagent-prototype/blob/f5b6a3270f390a8068413fdb61f6d2757c020a30/.scratch/long-term-memory/spec.md)
**Source:** 2026-11-07 实现审查；基线 da65294 至 bcf5ea6。

审查复现：记忆预算 65,536 字节，连续输入 320 个约 32 KB 的事件，记忆目录仅计量 18,012 字节，但 SQLite 中仍保留 318 个待处理正文，合计约 10 MiB；继续输入会继续增长。

- [ ] 为待接收材料建立明确、可计量的字节与条目上限，连同持久化队列、必要日志及暂存空间纳入有限容量合同，不另设无界缓冲区。
- [ ] 在达到上限前执行接收决策及背压；明确报告已接收、待处理、失败与暂未接收，不能先宣称接收成功再静默丢弃。
- [ ] 若使用源事件引用与补送游标替代重复正文，验证源记录的保留、可重放性及读取失败语义；不能把保留压力转移成另一个无限集合。
- [ ] 业务事实已经提交但记忆尚未接收时，崩溃重启后仍有有界、持久且幂等的恢复路径；容量恢复后逐步补送，重复事件只生效一次。
- [ ] 存储满、隔离边界拒绝写入、后台暂停、持续输入及并发接收均不突破待接收容量；不改变现行授权、活动任务或业务事实的一致性。
- [ ] 用 Runtime 集成测试覆盖 64 KiB 与超过 320 个大事件的压力，观测所有记忆相关持久化占用，而非只检查记忆目录；同时验证恢复补送和稳定的容量状态。
- [ ] 在现有健康状态中提供队列容量、占用、背压原因与恢复进度，操作者无需查数据库判断是否仍在无界增长。
